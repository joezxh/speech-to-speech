# 将静态 Space 改造为带搜索代理的 Docker 应用

为了让模型拥有网络搜索工具，在公开 Space 的浏览器中运行的执行器（executor）需要一个搜索密钥。一个 `sdk: static` 的 Space 以原样提供文件、没有运行时进程，因此无法在浏览器使用而不暴露该密钥的情况下保有一个密钥。我们将 Space 从 `sdk: static` 改造为 `sdk: docker`：单个容器运行一个小型服务器（FastAPI + uvicorn），它既**原样**提供现有的前端，又暴露一个同源的 `/search` 代理，在服务端保存 `SERPER_API_KEY`。整个应用都在这个容器中；s2s speech-to-speech 后端保持它本来的、独立的负载均衡服务。

## 考虑的备选方案

- **保持静态，仅由用户提供密钥**——没有所有者密钥；只有每个用户自行粘贴自己的密钥时搜索才可用。未选为默认值，因为那样部署后的 demo 将没有任何可用搜索。
- **独立的代理服务**——保密性相同，但将应用拆分到两次部署中。未采用：应用必须位于同一个容器中。
- **在构建时将密钥写入客户端 JS**——在提供的 bundle 中可被读取。未采用：这违背了初衷。

## 影响（Consequences）

- 部署不再是静态的：现在有了 Dockerfile 和一个服务器进程；README 的 front-matter 从 `sdk: static` 改为 `sdk: docker`。
- 客户端调用同源的 `/search`；服务器从环境变量读取密钥。用户仍可提供自己的密钥作为回退，按请求发送给代理。
- 前端、音频流水线和 s2s 握手均未被改动——只增加了托管的形态和新的路由。
