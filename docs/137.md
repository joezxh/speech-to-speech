### 发现并修复的 3 个缺陷

1. **TTS 永久失败（致命）**——发布镜像 `cu130-1.0` 构建时漏装 `python3-dev` → triton JIT 缺 `Python.h` → 每次生成 `CalledProcessError`，**服务跑得通但永远没有音频输出**（日志 `tts_ttfa=n/a`）。修复：`Dockerfile.ttsfix` 派生镜像补装 `python3.12-dev`（+ `sox` 消除告警）。
2. **启动永久卡死**——镜像内 `s2s_pipeline.py` 把 tagger 资源路径写成 `tokenizers/…`（实际在 `taggers/`）→ `nltk.data.find` 必失败 → 触发无超时的 `nltk.download()` → 容器卡在启动、Uvicorn 起不来。修复：镜像内补丁修正路径并把下载改为 30s 超时的守护线程。
3. **GPU 错绑导致 OOM 崩溃循环**——`docker compose` 只读 `.env`（不读 `.env.cu130`），`PIPELINE_GPU_ID` 回退 0，容器落到被 vLLM 占满的 GPU0 → CUDA OOM。修复：补建 `/home/jiangwei/speech-to-speech/.env`。

## 关于"独立服务端口"
两点关键事实：
1. **原本没有**独立的 ASR/TTS 端口——Qwen3-ASR 和 Qwen3-TTS 都只在 `speech-to-speech-pipeline-1`（端口 8765）**进程内**加载，仅供实时对话链路内部使用。
2. 137 上两块 RTX 4090 显存已被占满（GPU1 = pipeline ~8.8GB + 一个 32B vLLM ~38.5GB；GPU0 也被 vLLM 占满）。再起独立容器会因 OOM 起不来（之前那个 asr 容器反复重启就是这原因）。

因此正确做法是：**把 ASR/TTS 专用 REST 端点挂到现有 pipeline 服务（8765）上，复用其已加载的模型，零额外显存**。

## 新增端点（已在 137 实测通过）

**ASR — 语音转文字**（OpenAI 兼容 `POST /v1/audio/transcriptions`）
- 入参：`file`（multipart 音频）或请求体原始音频字节；可选表单 `language`（默认 `auto`）。
- 返回：`{"text": "...", "language": "..."}`
```bash
curl -F "file=@test.wav" -F "language=auto" http://192.168.1.137:8765/v1/audio/transcriptions
```
实测：输入英文语音 → 正确转写英文文本。

**TTS — 文字转语音**（OpenAI 兼容 `POST /v1/audio/speech`）
- 入参：JSON `{"input": "...", "voice": "Aiden", "language": "Chinese"|"English"|"Auto", "response_format": "wav"}` 或表单等效字段。
- 返回：`audio/wav`（16-bit PCM, mono, 24kHz）
```bash
curl -X POST http://192.168.1.137:8765/v1/audio/speech \
  -H "Content-Type: application/json" \
  -d '{"input":"你好，这是语音合成测试。","language":"Chinese","voice":"Aiden"}' -o out.wav
```
实测：中文/英文均生成有效 24kHz WAV。

## 注意事项
- 端点从 `pool[0].handlers` 按类型懒加载 `Qwen3ASRSTTHandler` / `Qwen3TTSHandler`，复用已加载模型，**不占额外显存**，realtime 服务（`/v1/realtime`、语音通话）完全不受影响。
- 若 pipeline 容器被**重建**（非 `docker restart`）补丁会丢失；重应用只需：把 `scripts/patch_pipeline_rest.py` 拷入容器执行一次再重启即可（补丁脚本已存于 `/home/jiangwei/speech-to-speech/scripts/`）。
- 并发说明：手动 ASR/TTS 调用与正在进行的实时会话共享同一模型，偶发时会互相挤占算力，适合 app 非高并发的直接调用场景。
