## 1. 总体思路

仓库没有引入第三方异常框架，而是采用「Python 内置异常 + 少量领域 `*Error` 子类 + 上游错误分类器」的组合。
- 参数/校验失败统一使用 `ValueError`。
- 业务语义错误（会话项、历史提交、运行时状态）定义为自定义 `RuntimeError` / `Exception` 子类。
- 配置解析路径上的所有诊断通过 `ConfigurationError` 抛出，保证不泄露敏感值。
- 面向 OpenAI Realtime 协议层的错误统一封装成 `openai.types.realtime.RealtimeErrorEvent`，由 handler 的 `make_error` 构造。
- LLM provider 侧的上游 HTTP 异常通过 `LLM/provider_errors.py` 的 `classify_provider_error` 归一化为 `(kind, detail)` 三元组，供上层做可观测性区分。

## 3. 架构约定

### 3.1 配置层：`ConfigurationError` 作为唯一出口
`config.py` 中的 `_error(document, path, message)` 是配置解析器的统一抛错入口。它从 `document.locations` 恢复行号，并把 `path` 用 `_ID.fullmatch` 过滤后拼接成安全路径，再抛出 `ConfigurationError`。调用方（如 `configured_runtime.py`）在捕获下游 `ValueError` 后重新包装为 `ConfigurationError`，确保配置错误始终携带位置信息且不泄露用户输入。

### 3.2 实时服务层：handler 返回 `RealtimeErrorEvent`
`handlers/base.py` 的 `RealtimeBaseHandler.make_error` 委托给 `service.make_error`，构造 `openai.types.realtime.RealtimeErrorEvent`。各 domain handler（audio/conversation/response/session）在参数校验失败时直接 `return self.make_error(...)`，而不是 raise，使 handler 方法可以混合返回正常结果与错误事件。

### 3.3 LLM provider 错误分类
`provider_errors.py` 维护一个 `httpx` 异常到 kind 的映射表，并通过 `_CLASS_NAME_KINDS` 把 OpenAI SDK 的 `APIConnectionError` / `APITimeoutError` / `APIStatusError` 分别归类。`classify_provider_error` 总是以 `str(exc)` 开头构造 `detail`，再追加 `upstream_status=...` 与 `upstream_body=...`（截断至 400 字符），供日志与测试断言复用。

### 3.4 资源清理与生命周期
`configured_runtime.py` 的 `_cleanup` 尝试调用资源的 `cleanup` / `reset` / `diarizer.reset`，捕获全部 `Exception` 并以 `logger.warning` 记录，避免清理失败掩盖主流程错误。`_run` 包裹 `except BaseException`，把 worker 崩溃转为 `_failure` 字符串并触发全局 stop。

## 4. 观察到的约定与约束

- **参数校验**：函数/类构造时的非法入参一律 raise `ValueError`（例如 `audio_client.py` 中对 URL、buffer 大小、tool schema 的校验），这是仓库中最常见的错误形式。
- **可选依赖缺失**：对 `mlx_lm`、`torch` 等可选后端使用 `try/except ImportError` 并在捕获处给出安装指引（见 `LLM/language_model.py`、`TTS/kokoro_handler.py`、`VAD/firered_vad_iterator.py` 等）。
- **上游网络错误**：LLM 侧通过 `provider_errors.classify_provider_error` 把 `httpx.TimeoutException` / `ConnectError` / `NetworkError` 以及 `status >= 500` 统一标记为 `upstream_unavailable`，以便上层区分“重试可能成功”的错误。
- **配置诊断安全**：`ConfigurationError` 的 docstring 明确声明其目的是“不回显输入值的 sanitized configuration diagnostic”；`_error` 强制只允许 schema 字段名与正则匹配的标识符出现在消息中。
- **运行时错误隔离**：`ConfiguredRuntimeError` 的 docstring 同样声明“不包含 provider 诊断或凭据”，用于向调用方暴露高层生命周期错误而不泄漏敏感细节。
- **会话/历史一致性**：`HistoryCommitError` 仅在 history 写入阶段抛出，且被外层 try/except 捕获后先 `reject` 再 re-raise，保证 rejected 响应不会留下半写状态。
- **未观察到**：仓库中没有 `panic`/`recover`（那是 Go 概念）、没有统一的 error middleware 中间件、也没有全局异常处理器；错误传播主要依靠 Python 异常链与 handler 返回值。
