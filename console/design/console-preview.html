需要重点关注

TTS 不可用（影响：所有会话都出不了声）

判定依据：tts handler not ready 在 300s 窗内连续 3 次、无任何成功指标；监控卡同段 loaded:false。

显存 91.4% + 一次 OOM（影响：新会话可能直接失败）

判定依据：vram_pressure 告警与 OOM 行同一时间窗；TTS 反复加载又失败会持续抬高占用。

STT p95 尖峰（影响：长语音尾部延迟变差）

判定依据：p95/p50 = 3.2，且同一时刻 slow request 只出现在 STT 与 LLM，VAD 正常。

可能根因

同卡四段共用一份显存，TTS 加载失败后反复重试

置信度：高（0.82）· 依据：91.4% 占用 + 3 次重试 + OOM 行在同一分钟。

STT 并发超过单卡吞吐

置信度：中（0.56）· 依据：p50 正常而 p95 抬高，典型的轻微排队；无错误行佐证。

可执行的优化方案

先降 num_pipelines 到 2，再重启 pipeline

预期：整卡占用降到 ~70%，给 TTS 腾出加载空间。风险：并发会话数上限减半。

把 TTS 换成更小量化，或先预热再放流量

预期：首会话不再承担 6.4 s 加载。风险：音色/质量可能变化，需回归。

STT 降 compute_type 或限制并发

预期：p95 回落到 500 ms 量级。风险：单次识别略慢。
